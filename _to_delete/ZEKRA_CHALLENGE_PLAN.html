01 Summary

  • A node challenges another to prove it executed a program correctly. The challenge is {@P, nce} — a program identifier and a fresh nonce — and lands on-chain before any proof exists.
  • The challenged node produces a zk-SNARK proof that its execution path is legal for the program's control-flow graph, without revealing the path or the CFG.
  • Every other node independently runs all three of the paper's verification checks and publishes its own verdict. This is what the blockchain adds: the paper has one verifier, here we get N mutually distrusting ones plus an immutable audit trail.
  • A node that cannot judge — missing reference, wrong verification key, verifier crash — abstains rather than guessing. Abstention never blocks consensus.

The single most important design decision is Option A (§4): a verifier never accepts public inputs from the party it is verifying, and instead reconstructs them from the signed on-chain reference plus the on-chain nonce. This is now proven byte-exact against real prover output.

02 The protocol as implemented

The challenge

Verifier  ---->  Prover        { @P , nce }

@P identifies the program, or the region of a program, to attest. nce is a fresh 254-bit nonce whose only job is freshness: it is hashed into the execution-path commitment and surfaces as a public circuit input, so a verifier can distinguish a fresh attestation from a replayed one.

Entry and exit nodes are not sent. They are reference values the verifier already holds and checks against what comes back — travelling in the opposite direction, inside the proof's public inputs.

What the verifier holds in advance

vk_C , tpk , { @P , h₁ = H(CFG‖r₁) , h₃ = H(M‖r₃) , n▷ , n◄ }

r₁ and r₃ are secrets held with the program materials, never given to verifiers, who only ever see the digests. This is what keeps the CFG private while still letting a party with no access to the program verify a proof about it.

The three checks

Accept  iff
  (1)  Vf( Sig , h₂ , tpk ) = 1                             -- path came from a real tracer
  (2)  x \ {h₂} == { H(CFG‖r₁) , H(M‖r₃) , n▷ , n◄ , nce }  -- the claim is the right claim
  (3)  Verify( vk_C , x , y , π ) = 1                       -- the SNARK

The original integration implemented only check (3). That is not enough: an old proof from a previous attestation passes (3) perfectly — it is a valid proof of a stale statement. Check (2) is the entire anti-replay mechanism. All three are now implemented.

03 Role mapping onto the blockchain

ZEKRA roleBlockchainNotes
Verifier the challenger and every other node The paper has one untrusted verifier; here N nodes independently run checks (1)–(3) and each records a verdict.
Prover the challenged node Prover and Worker are collapsed into one node — the Jetsons are not resource-constrained. Splitting the Worker out is a natural extension and arguably the more interesting blockchain angle.
Network operator out of band Runs KeyGen once; vk_C is distributed as a file and its digest pinned in the reference.

Role exhaustion. A node cannot verify its own work, so the number of independent verifiers is N − |{challenger, responder, miner}|. On a three-node network that is zero, which is why local testing uses five nodes. This caused real confusion during earlier testing — a silent third node looked like a bug, but was simply the miner.

04 Option A — the verifier rebuilds the public inputs

Letting the responder ship its own primary_input.bin is unsound. A dishonest responder could declare correct values in JSON while shipping a binary encoding different ones: check (3) passes (the proof genuinely matches the shipped file), check (2) passes (the declared values look right), and the two are unrelated.

Option A closes this structurally. The verifier discards anything the responder says about the claim and builds primary_input.bin itself:

n▷ , n◄ , h₁ , h₃   <- the authority-signed on-chain reference
nce                 <- the nonce on the request transaction, on-chain
h₂                  <- the responder (the one value that legitimately comes from it)

If the proof was generated for any other statement, check (3) fails. Check (2) therefore cannot be bypassed, because a lying responder never gets to state the claim.

h₂ being responder-supplied is correct: it is H(EP‖nce‖r₂), the commitment to the secret execution path. It is precisely what is being attested, and precisely what check (1)'s signature covers.

The serialization, confirmed empirically

primary_input.bin is an ASCII count, a newline, then N × 32-byte little-endian field elements in Montgomery form (a·R mod p, R = 2²⁵⁶ mod p), ordered: 

[ 1 , n▷ , n◄ , nce , h₁ , h₂ , h₃ ]

This was recovered by decoding real prover output, not from documentation. Verified: a reconstruction from the reference values is byte-identical to what run_prover_raw emitted, for all three test proofs.

05 Data model

Reference material — authority-signed, published on-chain

{
  "reference": {
    "program_id": "crc32",
    "h1": "...", "h3": "...",
    "entry_node": 3, "exit_node": 41,
    "vk_sha256": "<sha256 of verification_key.bin>",
    "circuit": {
      "adjlist_len": 64, "adjlist_levels": 9, "path_len": 128,
      "stack_depth": 8, "label_bitwidth": 7,
      "bucket_bitwidth": 4, "address_bitwidth": 32,
      "pruned": true
    }
  },
  "authority_pubkey": "<ed25519 hex>",
  "authority_sig": "<ed25519 hex>"
}

Rules, all implemented:

  • Ed25519-signed by a program authority. A node ignores references signed by anyone other than the authority it is configured to trust.
  • First valid reference for a program_id wins. A later transaction cannot redefine a program out from under existing attestations.
  • Circuit parameters are signed. h₁ depends on adjacency-list padding and the encoding bitwidths, not only on the CFG — resize the circuit and h₁ must be republished. Pinning the parameters is what makes that detectable.
  • vk_sha256 is enforced. A node holding a verification key other than the one the reference was issued against would reject every honest proof; it abstains instead, so its own misconfiguration cannot slander an honest prover.

On-chain rather than a config file: immutable, timestamped, and identical for every verifier by construction. Config files drift per node, and this codebase has already demonstrated how silently divergent per-node state behaves.

Challenge and response

The challenge is a request transaction carrying program_id and the nonce in function_parameter. The response carries h2, proof_b64, the prover's public key, and a signature over a canonical binding of {program_id, request_hash, nonce, h2}.

There is no primary_input_b64. Its absence is the point.

Two dedup notes: content-hash dedup cannot detect duplicate responses, because Groth16 is randomized and two honest proofs of the same statement differ byte-wise — parent-based dedup is used instead. A nonce-reuse guard rejects a challenge whose nonce already appeared on-chain.

06 CFG pruning — scope, and the authority's responsibility

prune_cfg.py reduces a CFG before circuit compilation. Pruning changes the adjacency list and the translator, therefore it changes h₁ and h₃, therefore the pruned artifacts are part of the signed program definition — not a local choice a prover may make. A prover that pruned locally would compute digests that do not match the reference, and _prove_real() aborts on exactly that mismatch. The reference carries an optional circuit.pruned flag so the prover formats the same files the authority did.

The prover needs no additional out-of-band knowledge: the tracer and translator shipped with the program materials already emit paths in the pruned label space. Nothing new is leaked either — the reference already publishes circuit dimensions (adjlist_len, path_len), which reveal about as much as the pruned bit does, and the CFG itself remains behind a hash.

Finding — the pruning mode is security-critical, and verifiers cannot see it

A verifier only ever sees h₁, a hash. Nothing in the protocol distinguishes a bidir slice from a path slice. The soundness of every attestation for a program therefore rests entirely on the authority having pruned correctly — which is precisely why the pruned CFG must come from the authority rather than from provers.

ModeKeepsEffect on attestation
path only the nodes and edges of one recorded trace Severely weakened. The attested CFG becomes the trace itself, so the forward-edge check degenerates to "execution used edges seen in one earlier run."
forward everything forward-reachable from the entry Conservative, safe
bidir (default) nodes both reachable from entry and able to reach exit Correct choice. Removes only code that can never appear in a valid entry→exit execution, preserving every branch a different input could legitimately take.

Pruning also narrows what is attested. If a CFG is pruned to a region of interest, control-flow hijacking outside that region produces a perfectly valid proof. This matches the paper — the attested region is normally a subset of the binary, e.g. one security-critical function — but it is a deliberate scope decision that should be recorded per program rather than inherited from whatever the extractor happened to emit.

Recommendation — open decision

Widen circuit.pruned from a boolean into a signed declaration: {"mode": "bidir", "region": "<name>"}. It cannot be verified by a verifier, but because the reference is authority-signed and immutable it becomes an accountable declaration — an auditor can see what security scope each program was registered under. One-line change; flagged as a decision rather than made unilaterally.

The one untested link

_prove_real() has three steps: format inputs → generate the witness in Java → prove. Steps 1 and 3 are exercised; step 2 is not, because compile_circuit.py bakes the input and output paths into the Java source and needs a JDK, and the available VM has only a JRE.

The design consequence: the circuit is compiled once against a fixed working directory, and each attestation rewrites inputs there and re-runs the already-compiled class. Closing this out needs one compile on a node with a JDK. It is a provisioning step, not a security gap — a misconfigured prover produces no witness and therefore no proof, and an absent proof is not a false attestation.

Defects found while wiring the real prover

Recorded because both were caught by rechecking rather than by testing the happy path.

  • _prove_real() used sys.executable with sys never imported — a guaranteed NameError the first time any node attempted to prove.
  • Pruned-CFG programs were unprovable. Nothing told the prover which CFG variant the authority had signed, so the formatter read the wrong files and produced digests that could never match. Not a security hole — the h₁/h₃ cross-check refused to proceed — but it made a whole class of program impossible to attest.

A third is worth recording as a testing lesson: the first real-mode run reported four attacks "caught" that were in fact all dying on a malformed request before reaching the check under test — a false green. The suite now asserts the reason for each rejection, not just the verdict.

08 Known gaps

Full list in ISSUES.md (13 entries). The ones that matter for attestation:

#GapConsequence
10 Only the first response in a block is verified A second attestation riding in the same block is adopted into permanent history unverified. Deliberately deferred; the fix is to verify every response in the block.
11 Licensing is not enforced Any node holding program materials may attest; nothing checks it was authorised to. The paper notes (§5) that anyone knowing a CFG can identify satisfying paths, so leaked materials mean valid-looking attestations. Currently mitigated only by distribution discipline.
3 No consensus rule behind verdicts Verdicts are recorded, but nothing aggregates them into a decision.
